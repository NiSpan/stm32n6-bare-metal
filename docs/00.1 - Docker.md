## Why Docker

The toolchain and tools don't go on the host. They go in a **Docker image**: a packaged Linux environment with exactly the tools and versions I chose. A **container** is a running instance of that image.

Why this is common practice in embedded development:

- **Same environment everywhere**: the image is defined by one file (`dockerfile`), so another PC gets exactly the same compiler version and tools.
- **Host stays clean**: no cross toolchains or build dependencies installed on the PC, and no conflicts between projects that need different versions.
- **Easy to rebuild or throw away**: a broken environment is fixed by rebuilding the image, not by repairing the host.

My project folder is shared with the container, so I edit files on the host (Neovim) and build inside the container.

## Installing Docker on the host

I installed Docker Engine from **Docker's official apt repository**, following [Install Docker Engine on Debian](https://docs.docker.com/engine/install/debian/). Debian also has its own `docker.io` package, but Docker's repository has newer versions and includes the Compose plugin.

Packages: `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`.

To run Docker without `sudo`, add the user to the `docker` group and log in again:

```sh
sudo usermod -aG docker $USER
```

Members of the `docker` group effectively have root access to the host, which is fine on a personal machine.

Check:

```sh
docker --version          # Docker version 29.x
docker compose version    # Docker Compose version v5.x
docker run --rm hello-world
```

> [!note] Docker service
> Docker runs as a background service (`docker` daemon), managed by systemd.
>
> ```sh
> sudo systemctl status docker     # is it running?
> sudo systemctl start docker      # start it now
> sudo systemctl enable docker     # start it automatically at boot
> ```

## The image: dockerfile

The `dockerfile` (in the project root) describes **what is inside** the image. Each instruction adds a layer; Docker caches layers, so a rebuild only redoes the steps after the first change.

```dockerfile
FROM debian:13

RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        gcc-arm-none-eabi \
        binutils-arm-none-eabi \
        gdb-multiarch \
        make \
        cmake \
        ninja-build \
        git \
        usbutils \
        ca-certificates && \
    rm -rf /var/lib/apt/lists/*

# --- OpenOCD from upstream source (Debian's 0.12 package lacks STM32N6) ---
ARG OPENOCD_REF=master
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential autoconf automake libtool pkg-config texinfo \
        libusb-1.0-0-dev libjim-dev && \
    git clone https://github.com/openocd-org/openocd.git /tmp/openocd && \
    cd /tmp/openocd && \
    git checkout ${OPENOCD_REF} && \
    git submodule update --init --recursive && \
    ./bootstrap && \
    ./configure --prefix=/usr/local --enable-stlink && \
    make -j"$(nproc)" && \
    make install && \
    cd / && rm -rf /tmp/openocd && \
    rm -rf /var/lib/apt/lists/*

ARG USER_UID=1000
ARG USER_GID=1000

RUN groupadd -g ${USER_GID} developer && useradd -m -u ${USER_UID} -g ${USER_GID} -s /bin/bash developer

WORKDIR /workspace

CMD ["/bin/bash"]
```

| Part                        | What it does                                                                                       |
| --------------------------- | -------------------------------------------------------------------------------------------------- |
| `FROM debian:13`            | Base image: same Debian as the host.                                                               |
| `RUN apt-get ...`           | Installs the tools. One `RUN` with `&&` = one layer.                                               |
| `--no-install-recommends`   | Only the listed packages, not their optional extras: smaller image.                                |
| `rm -rf /var/lib/apt/lists/*` | Deletes the apt package index after installing: smaller image.                                   |
| Toolchain packages          | `gcc-arm-none-eabi`, `binutils-arm-none-eabi`, `gdb-multiarch`.                                    |
| `make`, `cmake`             | Build tools: CMake generates Makefiles, Make runs them ([11](<11 - Make and CMake.md>)). (`ninja-build`: installed, not used yet.) |
| `git`, `ca-certificates`    | Cloning repositories over HTTPS (needed for the OpenOCD build).                                    |
| `usbutils`                  | `lsusb`, to check the ST-LINK is visible in the container.                                         |
| OpenOCD block               | Builds OpenOCD from upstream source: the Debian package (0.12) has no STM32N6 support. Build deps: host compiler and autotools, `libusb` (talks to the ST-LINK), `jimtcl` (Tcl interpreter for OpenOCD scripts). Source is deleted after `make install`. |
| `ARG OPENOCD_REF=master`    | Build argument: which OpenOCD version to build. Pin it with `--build-arg OPENOCD_REF=<commit>`.    |
| `useradd ... developer`     | A normal user with my host UID/GID (1000), so files created in the container belong to me on the host, not to root. |
| `WORKDIR /workspace`        | Default directory in the container. Not used any more: `compose.yaml` overrides it with `working_dir`. |
| `CMD ["/bin/bash"]`         | Command run when the container starts: a shell.                                                    |

## Running it: compose.yaml

The dockerfile says what is **in** the image; `compose.yaml` says **how to run** it, so I don't have to type long `docker run` options.

```yaml
services:
  stm32-dev:
    build: .
    image: stm32-dev:1.0
    # Mount this folder at the SAME path as on the host (run compose from
    # this folder, so ${PWD} is it). CMake writes absolute paths into
    # build/compile_commands.json; identical paths let clangd on the host
    # use that file directly.
    working_dir: ${PWD}
    volumes:
      - ${PWD}:${PWD}
    user: "${UID:-1000}:${GID:-1000}"
    # Pass the host USB bus so the ST-LINK is visible inside.
    # After unplugging/replugging the board, restart the container.
    devices:
      - /dev/bus/usb:/dev/bus/usb
    stdin_open: true
    tty: true
```

| Option                   | What it does                                                                     |
| ------------------------ | -------------------------------------------------------------------------------- |
| `services: stm32-dev`    | Name of the service, used in every `docker compose` command.                     |
| `build: .`               | Build the image from the `dockerfile` in this folder.                            |
| `image: stm32-dev:1.0`   | Name and tag of the built image.                                                 |
| `volumes: ${PWD}:${PWD}` | Mounts the project folder at the **same path** in the container as on the host. Same files on both sides: edit on the host, build in the container. Same path also means the absolute paths CMake writes into `build/compile_commands.json` are valid on the host, so clangd can use them. `${PWD}` is the current folder, so `docker compose` must be run from the project folder. |
| `working_dir: ${PWD}`    | The shell starts in the project folder. Overrides `WORKDIR` from the dockerfile. |
| `user`                   | Run as my UID/GID (default 1000), not root.                                      |
| `devices: /dev/bus/usb`  | Passes the host USB bus into the container, so OpenOCD can reach the ST-LINK. Device permissions come from the host's udev rule (see [Board access](<00.2 - Board access.md>)). |
| `stdin_open`, `tty`      | Interactive terminal (like `docker run -it`).                                    |

## Everyday commands

The run command, piece by piece: `docker compose run --rm stm32-dev`

| Argument    | Meaning                                           |
| ----------- | ------------------------------------------------- |
| `docker`    | Docker command-line tool                          |
| `compose`   | Use Docker Compose (reads `compose.yaml`)         |
| `run`       | Create and start a new container                  |
| `--rm`      | Remove the container when it exits                |
| `stm32-dev` | Service name defined in `compose.yaml`            |

Anything after the service name is the command to run instead of `bash`, e.g. `docker compose run --rm stm32-dev cmake --build build`.

| Command                                     | Purpose                                                      |
| ------------------------------------------- | ------------------------------------------------------------ |
| `docker compose build`                      | Build or rebuild the image                                   |
| `docker compose run --rm stm32-dev`         | Shell in a new, temporary container                          |
| `docker compose run --rm stm32-dev cmake --build build` | Run one command and exit                         |
| `docker compose up -d`                      | Start the service container in the background               |
| `docker compose exec stm32-dev bash`        | Open a shell in the running container (repeat per terminal) |
| `docker compose ps`                         | List running Compose services                                |
| `docker compose down`                       | Stop and remove Compose containers and networks              |
| `docker images`                             | List available images                                        |
| `docker ps -a`                              | List all containers, also stopped ones                       |
| `docker compose run --rm stm32-dev lsusb`   | Check the board is visible: `0483:3754 STMicroelectronics STLINK-V3` |

> [!warning]
> Each `docker compose run` starts a **separate** container with its own network. GDB in one `run` cannot reach OpenOCD in another `run` on `localhost:3333`. Use `up -d` + `exec` instead.
